# V3-1.2 通用门户会话 Broker 与 B站 Cookie 策略开发计划

日期：2026-09-17。状态：`DOCUMENT PASS / HIGH-RISK IMPLEMENTATION AUTHORIZED`。

## 1. 目标与范围

V3-1.2 在 V3-1.1 已外部限定 PASS 的 `MediaPortalAdapter` 之上，新增可扩展的门户会话能力层。首个实例只是 B站，但通用 UI、合同和 Broker 不得依赖 `bvid/cid`、B站 Cookie 名称或 B站 host。

本子阶段只交付：

1. 通用 `PortalSessionAdapter` / `PortalSessionRegistry` / `PortalSessionBroker`。
2. 只由扩展页面真实用户点击触发的 `PortalPermissionClient`。
3. 持久化五项 scope 决定但不持久化秘密的 `MediaConsentPolicyStore`。
4. B站专属 `BilibiliPortalSessionAdapter` 和 `bilibili-cookie-policy/v1`。
5. 只向 UI 返回 `PortalSessionCapability`；`available` 仅表示必需会话 Cookie 存在且非空，`serverValidated=false`。

本子阶段不实现一次性 credential envelope、Runtime 传输、`PortalCredentialLease`、cookiefile、字幕正文、媒体下载或 tabCapture。这些属于 V3-1.3 或 V3-2。

## 3. 目标架构

```text
Side Panel MediaConsentCard
  -> PortalPermissionClient.request(adapterId)       # 用户点击处理器内直接 chrome.permissions.request
  -> PortalSessionBroker.recordGrant(adapterId)      # Background 复核 permissions.contains
  -> MediaConsentPolicyStore                         # 仅决定、scope、revision、时间

Side Panel / Workspace
  -> PortalSessionBroker.inspectCapability(adapterId)
  -> PortalSessionRegistry.resolve(adapterId)
  -> BilibiliPortalSessionAdapter
  -> chrome.permissions.contains
  -> chrome.cookies.getAll({ domain: ".bilibili.com" })
  -> 白名单过滤与内存派生
  -> PortalSessionCapability                         # 不含 Cookie 值和名称列表
```

未来门户只能新增独立 `PortalSessionAdapter` 实现与注册表项：

```text
YouTubeMediaPortalAdapter     + YouTubePortalSessionAdapter     + youtube secret policy
XiaohongshuMediaPortalAdapter + XiaohongshuPortalSessionAdapter + xiaohongshu secret policy
```

新门户不得继承 B站的 host permission、Cookie 名称、scope 文案、样本 PASS 或服务端验证结论。运行时远程 adapter 继续禁止。

## 5. 不变式

1. `PortalPermissionClient` 是唯一可调用 `chrome.permissions.request` 的生产实体；调用点必须是扩展页面可见按钮的信任 click handler。
2. Background 不代替 UI 请求权限，只使用 `chrome.permissions.contains/remove`。
3. `PortalSessionBroker` 在任何 Cookie API 调用前必须同时复核产品 policy、revision、named permission 和 host permission。
4. `chrome.cookies.getAll` 返回的值只在 B站 adapter 单次调用栈内存在；返回前清除引用。
5. UI/message/storage/log/Trace/EventStore/error/retry/e2e/public evidence 中均不得出现 Cookie 值、完整 Cookie header 或可逆值 hash。
6. `available` 不等于 Cookie 在 B站服务端有效；合同固定 `serverValidated=false`。
7. capability observation TTL 固定 30 秒；超时、撤销、权限变化或 service worker 重启后重新读取，不得返回旧成功。
8. V3-1.2 不创建 task lease，不向 Runtime 发秘密，不修改 V3-1.1 封存 run。
9. 新门户必须有独立策略注册项和真实登录/未登录矩阵；没有注册项则 `V3_MEDIA_SESSION_ADAPTER_UNSUPPORTED`。

## 6. 测试与真实数据

- 单元测试：注册表唯一性、权限精确集合、policy 转移、默认拒绝、9 名白名单、值不可序列化、过期和撤销。
- 合同测试：Schema meta-validation；正例 shape；缺字段/多字段/非法 status 负例；B站 scope 与 registry 集合精确一致。
- 静态审计：构建 manifest 只新增 `optional_permissions=[cookies]` 和 `optional_host_permissions=[https://*.bilibili.com/*]`；必需 permissions/hosts 不放宽；0 全站 wildcard。
- 真实 Chrome 匿名 profile：授权后必须 `unavailable` + `V3_MEDIA_SESSION_COOKIE_MISSING`。
- 真实 Chrome 正例 profile：优先使用 `human_manual_login`；用户已明确授权时也可按补充条款使用 `user_authorized_live_session_seed`。后者必须经真实服务端验证，只能证明产品从 Cookie Store 派生候选能力，不得冒充人工登录路径。
- 真实撤销：用户点击撤销后 `permissions.contains=false`，policy=`revoked`，任何新 inspect 不得调用 Cookie API。
- 密密扫描：collector 在进程内短暂持有本 run 的原始值用于扫描全部持久/公开产物，只输出命中数与名称集合 hash；不输出值或值 hash。

## 7. 顺序、停止点与交接

1. 冻结本计划、验收计划、威胁模型、Schema/registry/fixture。
2. 内部文档审计 Fatal=0/Major=0。
3. 平铺外审包不超过 20 文件，Claude Code CLI 独立文档审计 Fatal=0/Major=0。
4. 用户单独批准 `V3-1.2 Cookie permission/session capability implementation`；本轮授权已记录。
5. 按 V3-1.2-0..6 实施，每段先写子阶段验收卡再改代码。
6. 使用匿名和专用登录 profile 完成同一新 run 的生产验收，再做 PRD review、false-green audit 和外部实现审计。

任一情况立即停止：需要复制主 profile；需要自动输入凭据；Cookie 值出现在持久介质；权限超出注册表；需要在 V3-1.2 内传输值到 Runtime；真实登录正例不可用；发现服务端验证才能决定本地 capability 却仍尝试声明 `available`。
