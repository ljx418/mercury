## 3. 设计闭环

- 主 bearer 只在 extension UI memory，用于 exact-Origin channel bootstrap；Background 只接收短期 ticket。
- Background sender、policy、permission、capability、adapter 和白名单均在 Cookie read 前重查。
- lease exchange 使用专用 fetch，通用 runtime proxy 双端拒绝；request body 不进入持久 observability。
- 第一次 request 即消费 channel；不确定失败不得重试同 body；公开 lease 无 secret/capability token。
- 撤销、Cookie/permission 变化、expiry、Runtime restart 和 Background restart 均有 fail-closed 结果与残余时间上界。
- B站字段只存在于 registry/plugin；未来门户不能继承 B站策略或 PASS。

## 4. Minor

1. **M-1 Background fetch Origin 实测前置**：Chrome 官方资料确认 service worker/extension page 具有独立 extension origin并支持跨域 fetch，但未在本文档环境中直接证明 loopback POST 的实际 `Origin` header 字节。`V3-1.3-1` 必须先做真实 Chrome probe；若 header 缺失或不稳定，停止并回到架构选择，不得放宽为任意/无 Origin。
2. **M-2 60 秒租约只覆盖本阶段**：V3-1.3 不下载媒体；60 秒足以验证 transport/lifecycle。V3-2 若证明下载启动需要更长 credential 生命周期，必须采用同任务受控续租并重新威胁建模，不能直接延长现有 lease。
3. **M-3 Runtime token 用户文案**：当前 `LocalRuntimeAccess` 标题是“本地文件访问”。实现 channel bootstrap 时需改成明确的“本地 Runtime 受控会话”，并说明 token 只在页面内存使用；不得新建持久 token 输入或暗示 Cookie 值被保存。
