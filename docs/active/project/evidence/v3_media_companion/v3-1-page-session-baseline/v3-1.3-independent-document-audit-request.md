# V3-1.3 一次性凭据通道文档候选独立审查请求

日期：2026-09-17。审查类型：只读、独立、文档与机器合同准备度审查。

## 1. 阅读顺序

先读本文件与 `AUDIT_MANIFEST.md`，再按 02..19 顺序。不得使用旧 external package、旧报告生成器或旧 validator 覆盖本轮结论。

## 2. 决策对象

判断 V3-1.3 文档是否足以支持后续自动实现以下唯一范围：

```text
exact extension Origin + existing in-memory Runtime bearer
-> 20s one-shot channel
-> trusted Background Bilibili allowlisted credential envelope
-> dedicated loopback fetch without body observability/retry
-> 60s Runtime process-memory lease
-> public secret-free lease metadata
```

不审查或放行媒体下载、ASR、OCR、VLM、完整视频理解、YouTube/小红书、V4 知识能力。

## 3. 必做独立验证

1. 重算 manifest 中 19 项 payload SHA-256，必须 19/19。
2. 重算 `10-session-policy-registry.json` 原始 hash，并与 `11-transport-policy-registry.json.sourceSessionPolicy.sha256` 对账。
3. 重算 B站 9 名集合的 C-sort + UTF-8 + trailing LF SHA-256，并与 transport policy 的 expected hash 对账。
4. Draft 2020-12 meta-validate `12-credential-lease.schema.json`；校验 `13-positive.json`。
5. 独立应用 `14-fixtures.json` 的 25 cases：12 schema negative 必须 invalid；13 semantic case 必须 schema-valid，并判断 exact FailureCode 设计是否无歧义。
6. 解析 `09-v3-media-companion-gap.drawio`：必须 8 页、ID 唯一、边引用完整、1600x900 页面内无顶层节点越界；抽样核对第 2/4/7/8 页文本与 MD 一致。
7. 对照当前仓库代码事实：通用 Runtime CORS、knowledge bearer、`runtimeClient` E2E body observation、Background generic proxy、V3-1.2 session code。判断目标文件、依赖方向和分期是否可实现。
8. 威胁审查：Origin spoofing、content-script confused deputy、ticket/envelope replay、TOCTOU、response-loss retry、body/log/error/Trace 泄漏、Runtime/Background restart、撤销竞态、未来门户误继承。
9. 判断 A01-A20 是否能拒绝 mock、跨 run、手改 lease、仅 UI badge、仅 Schema shape 和 Cookie 值 hash 等假绿。
10. 检查 V3-1.2 QUALIFIED PASS 是否保持；V3-1.3 是否仍为 implementation NO-GO；不得扩大成 V3/V3-2 通过。

## 4. 特别问题

- Browser service worker loopback fetch 的 Origin header 是不是必须先通过真实 Chrome probe？若不成立，是否存在不降低安全边界的备选路线？
- 20 秒 channel / 60 秒 lease 是否足以完成 V3-1.3 的传输验收，同时不提前承诺 V3-2 下载时长？
- 主 bearer 只用于 UI bootstrap、Background 只获 scoped ticket，是否比把主 bearer 直接交给 Background 更符合最小权限？
- public JSON Schema 不保存 secret envelope 实例、实现只用严格进程内类型，是否足够可实施和可审计？
