# Navia 项目阶段循环与跨会话交接规则

状态：项目级工作方式。适用于后续 V1/V2/V3/V4 等单一开发阶段；具体产品范围、合同、固定分母和阶段出门结论仍以相应 PRD、架构、开发/验收计划及最新审计为准。本文件不授权任何尚未获批的代码开发、云调用、权限扩大或人类代签。

## 1. 单一阶段的六步循环

1. **原型开发**：以当前代码、已批准 PRD 和目标架构为事实基线，形成用户体验路径与可交互原型。外部生成的页面或图像是候选，不是实现事实。
2. **原型审查**：人类对目标体验、当前基线、功能边界及操作路径进行审查。审查结论和偏差单独落盘。
3. **阶段性原型优化**：根据审查反馈迭代原型，直至目标体验可理解、可操作、可验收；未获代码开发批准前只改原型和文档。
4. **开发文档迭代**：重复“体验对齐 -> 开发文档撰写 -> 内部风险闭环 -> 独立文档审查”，直至 PRD、架构、组件/路由、里程碑、合同、开发计划和验收门槛相互一致。Codex 维护文档权威并使用隔离的 Codex 独立 Agent 做只读审查；ClaudeCode CLI 不承担文档外审。对外审计包仍遵守 `EXTERNAL_AUDIT_PACKAGE_PROCESS.md`。
5. **开发迭代**：取得明确的阶段/子阶段实施授权后，按文档顺序逐子阶段开发和验收；未关闭 Fatal/Major、假绿或高风险问题不得进入下一子阶段。
6. **阶段性审查**：依次执行原始 PRD 对照、代码/文档/架构图核查、全量端到端验收、中文可视化报告、独立复核、限定出门判断和范围内 Git 同步。不能通过时返回相应的计划或开发步骤，不发布全绿声明。

“文档方向认可”“原型认可”“某阶段限定 PASS”不自动转化为后续代码、凭据、云端上传或最终验收授权。每次变更以当前用户明确授权和阶段门禁为准。已封存的失败证据、旧 run 和审查结论不得改写成通过。

## 2. 中断、换机和重开窗口

- **中断后继续**：先检查最新用户指令、工作树、运行会话、主 PRD/架构/计划、最新审计和停止记录；识别最后一个通过的门禁与下一项可自动执行任务。可以继续时从该任务恢复，不重做已封存阶段，不覆盖用户改动。
- **无可继续任务时**：若文档不足、需要新增高风险授权、存在未闭环 Fatal/Major 或验证有假绿风险，停止实施。向用户发送最近相关的进展、阻塞原因、证据路径、可选路线及所需决定；不粘贴秘密或冗长原始聊天。
- **更换电脑后继续**：重新核对仓库版本、源码实体、架构图、依赖/模型/本机服务、私有数据可用性、开发计划和审计状态；列出下一阶段大纲及文档覆盖缺口。旧机器上的服务、Cookie、模型和私有证据不能假定在新机器可用。
- **重开窗口后继续**：对照 PRD 列出已实现且已验收、受限完成、未实现和不属于当前阶段的目标；判断计划是否完成。未完成则评估文档能否支撑下一项自动化开发，已完成则给出后续大纲或备选目标。

跨会话状态记录至少包含：目标/当前授权、最后通过门禁、未通过门禁、权威源码与文档路径、真实 run 与 seal、测试和人工签署状态、未关闭风险、下一条命令或下一项决策。状态摘要不能代替重读实际文件。

### 2.1 固定进展汇报与实现终端交接格式

当用户询问“当前进展”“还剩什么”“ClaudeCode 接下来做什么”，或任务因门禁、限额、重启、换机而暂停后恢复时，回复与持久化交接记录必须同时包含以下内容：

1. **精确阶段坐标**：使用 `版本阶段 / 工作包 / 子阶段 / 门禁状态` 表达，例如 `V3 completion / WP0 / R1 correction / NO-GO`；不得只说“正在开发 V3”或“快完成”。
2. **全局路线位置**：列出完整工作包主线，明确标记已通过、当前进行、未启动和被阻塞项；局部测试通过不得写成整个工作包或整个版本通过。
3. **门禁事实**：分别写明最后通过的门禁、当前未通过的门禁、Fatal/Major/Minor、证据目录和停止原因。若 verifier 因冻结基线过期而失败，必须区分“实现缺陷”和“冻结证据待更新”。
4. **下一执行边界**：明确 ClaudeCode 或其他实现终端只允许做什么、禁止做什么、完成后必须停在哪个状态，以及由 Codex、人类或独立审查承担的下一门禁。
5. **可复制提示词**：每次需要用户驱动外部实现终端时，提供一段可直接粘贴的完整提示词，包含工作目录、必读文件、范围、实现顺序、测试命令、声音/隐私/工作树约束、交付格式和停止条件；不得只给一句“继续开发”。
6. **恢复触发条件**：记录任务为何停止、满足什么事实后才能继续，以及继续时从哪一项开始；不得重复已封存阶段，也不得越过未关闭 Major。
7. **事实落盘**：把上述状态写入当前阶段 receipt/handoff/audit 或本项目工作流文档。对话摘要是导航信息，不替代仓库内权威记录。

默认角色分工保持为：Codex 负责 PRD、架构、冻结合同、计划纠偏、门禁判定和阶段验收；ClaudeCode 负责获得授权范围内的产品代码实现、开发自验证与实现交接；独立文档审查由隔离的 Codex Agent 完成；人类仅处理明确列出的高风险授权和真实体验签署。

## 3. 原型与外部设计协作

- 需要 Gemini 协作时，准备**同一目录、总文件数不超过 10**的可独立审查包：当前 PRD、目标体验与边界、架构和路由、当前源码的有界摘录或融合 HTML、真实基线截图、可交互组件/页面候选、已知问题及事实核查清单。附一段面向 Gemini 的明确提示词，在对话框交付；不得将私有凭据、Cookie、原始私有媒体打包。
- Gemini 或其他生成工具返回代码时，只替换经审查的原型候选；审查页同时保留认可的概念图、真实基线图和目标交互。候选与 PRD、代码事实冲突时先修订，不直接作为产品实现。
- 阶段性前端优化只做概念和原型，直到用户批准实际开发。审查 HTML 应包括目标概念图、实际基线截图、总体/模块设计、可操作的交付级组件、逐组件功能与交互说明，以及每条 PRD 用户路径的步骤图。生成图只作设计表达，必须检查术语、状态、架构实体、数据来源和事实错误；技术架构优先使用 Archify，Draw.io/HTML/SVG 可作可核查兜底。完成后提供可打开的页面供人类审阅。

## 4. 文档冻结与审查

1. 以已批准 PRD、原型和当前源码重建阶段架构与里程碑，使用 Archify 辅助梳理；更新 PRD 增量、目标架构、开发大纲、详细开发/验收计划、风险 ADR、组件/路由合同和 Gap 图。不得因新方案删除既有有效分母或历史证据。
2. Draw.io 最多 8 页、中文书写；用明确的代码实体、分层、调用/数据关系与颜色状态区分已实现、开发中、待修改、未实现。图中同时展示当前/目标差异、目标体验、计划、里程碑、验收步骤、出门条件与风险，避免重复冲突和抽象口号。
3. 每条验收义务都要有用户场景、操作步骤、可观察结果、固定分母/出门阈值及失败处置；不得出现无场景、无步骤、无具体门槛的“三无验收”。合同、PRD、图纸和原型须可相互追踪。
4. 内部审查检查规格偏移、架构可实现性、依赖环、数据/授权生命周期、虚假验收、未落盘问题和技术路线成本。可修复问题继续文档迭代；不可消减的重大风险列出路线优劣供用户选择。用户审阅图纸后，必要时提交外部独立审查。
5. 外审包清空重建、平铺、不超过 20 文件（含 manifest）；列明入口、载荷哈希、待审结论和明确的限定声明。文档和实施出门审查由不参与被审实现的 Codex 独立 Agent 执行；审查意见要在权威 MD/Draw.io 中逐条闭环。外审通过仍不等于实施批准。

## 4.1 Codex 与 ClaudeCode 的固定职责

- **Codex 主会话**：负责 PRD、架构、合同、开发/验收计划、阶段门禁、交接包、证据抽查、独立验收组织和最终出门判断。
- **Codex 独立 Agent**：负责只读文档审查和实施候选复算；不得参与被审代码实现，不得代签人类验收。
- **ClaudeCode CLI**：只负责一个已冻结工作包内的实际代码实现、自验证、真实数据运行和实施 handoff；不得修改阶段目标、降低验收分母、宣布阶段 PASS 或承担独立外审。
- **用户**：手动逐阶段启动 ClaudeCode；只处理明确的高风险授权、不可自动化的体验判断和最终人类签署。

每次只向 ClaudeCode 交付一个工作包。ClaudeCode 完成并停止后，Codex 先核对 diff、测试、真实 run、证据和 PRD 映射，再决定通过、打回或冻结下一工作包。不得让同一个 ClaudeCode 会话既实现又签署独立出门结论。

每次需要用户驱动 ClaudeCode CLI 时，Codex 必须在聊天中提供**完整、可直接复制粘贴**的
提示词；若提示词已落盘，也必须明确列出唯一文件路径，并给出一条可直接复制完整内容的命令。
不得只给章节名、摘要、多个候选路径或要求用户自行拼接上下文。提示词必须包含当前门禁、
授权范围、必读文件、实施目标、禁止项、验证命令/门槛、证据交付和停止条件。

## 5. 实施与逐子阶段验收

- 开始每个子阶段前，依据总 PRD 单独落盘详细开发计划、验收计划、实施前审计和风险清单；Fatal/Major 规格偏差或假绿风险必须先关闭。
- 每个子阶段完成后，用真实数据执行端到端用户路径、合同/负例、故障/恢复、隐私和资源检查，并单独落盘 PRD 规格检视、验收结果、审计意见与下一阶段交接。Mock、旧 run 拼接、降低阈值或用户主观判断不能替代生产证据。
- 验收失败回到开发计划，分析根因并生成新候选；需要扩大权限、改变架构/产品承诺、上传私有内容或其他高风险处置时停止并向用户说明影响、路线与取舍。人类只处理必须由人类完成的授权和体验判断，不承担机器可自动验证的工作。
- 停止或中断时，在对话框明确写出“自动化开发停止原因”、当前门禁和下一个可执行动作。不得以测试通过概括未完成的 PRD 体验。

### 5.1 验收分层与防重复返工规则

以下规则源自 V3 WP0 R0-R2 的冻结漂移、逐缺陷反复验收和 byte-cap
false-green 复盘。它们适用于所有后续工作包，并优先约束“每次修改都重新做完整外审”的
低效做法。

#### A. 三层验收模型

1. **实现内循环**：实现者每次修改只执行受影响模块的定向单测、合同负例、类型检查和
   必要静态门禁。该层用于快速定位，不产出阶段 PASS，也不触发独立外审。
2. **子阶段 checkpoint**：一个预先冻结的工作包全部实现后，统一执行一次相关子树回归、
   受影响 verifier、PRD 映射和 Codex checkpoint。checkpoint 应一次汇总全部 Fatal/Major/
   Minor，输出一个限定纠偏包，不把同一批问题拆成多轮独立审查。
3. **阶段 closeout**：只有阶段所有工作包完成后才执行全量 E2E、真实数据分母、可视化报告、
   独立实施审查、人工体验和 Git 同步。纠偏中的单文件变化不得反复触发阶段级全量外审。

除非变更触及公共合同、安全边界、固定分母或真实数据有效性，否则不得从实现内循环直接
升级到阶段 closeout。

#### B. 单批纠偏和停止规则

- Codex 在 checkpoint 中应先完成源码、测试、证据和生产接线的整体检视，再一次性列出该
  工作包的全部已知问题；同根因问题合并为一个纠偏包。
- ClaudeCode 按纠偏包完整实现并自验证，状态写 `AWAITING CODEX CHECKPOINT` 后停止。
  Codex 只做一次复核；若原问题已关闭且无新 Fatal/Major，直接放行下一工作包。
- 只有新证据暴露了此前无法观察的独立缺陷，才允许新增纠偏轮次。文案差异、重复发现、
  同一冻结哈希漂移或已知测试失败不得包装成新的审查轮次。
- 文档外审用于“规格是否足以实施”的冻结点，不用于每次代码修正。实施纠偏默认只需要
  实现自验证和 Codex checkpoint；完整独立外审留到阶段 closeout 或安全/公共合同变化。

#### C. 防 false-green 验证

每条关键验收义务必须建立 `义务 -> 生产调用路径 -> 测试驱动 -> 明确 oracle -> 负例 ->
清理/终态` 映射，并遵守：

- 测试名称、常量存在、字符串搜索、返回值类型或 exit 0 不能单独证明行为成立。
- 上限测试必须命中目标上限本身，验证 exact boundary 和 one-over；不得先触发另一个更小
  的队列、长度或权限限制后仍宣称目标上限已验证。
- timeout 必须在没有后续输入的情况下由 fake clock 主动触发；“下一消息到达时才检查”不
  等于 deadline。
- fail-closed 必须同时断言拒绝发生前后状态、未写入/未入队、固定错误码、producer/consumer
  停止、terminal settle、临时资源与 marker 清理；静态检查只能作为补充。
- composition 测试必须驱动实际生产类和真实接线边界。Mock 可以替代浏览器/网络原语，但
  不能替代被验收的 owner、adapter、router 或状态机。
- 证据文档中的每个“已验证”必须能指向实际断言。若测试只是固定值或 shape 检查，应写成
  “合同存在性验证”，不得写成“运行行为验证”。

#### D. 冻结证据与活动源码

- 冻结合同验证器应分别表达合同、source inventory 和目标实现 scope；不得因活动实现文件
  的正常修改而跳过整文件语义抽取，再把缺失结果误报为产品实现缺陷。
- 哈希不一致首先分类为“实现缺陷、未授权漂移、冻结证据过期”三者之一。确认只是已授权
  实现导致的冻结证据过期时，由 Codex 在工作包稳定后一次性受限重冻结，不要求实现者反复
  改代码迎合旧哈希。
- 不得在每个纠偏小轮重冻结。重冻结只能发生在实现结构稳定、测试通过、scope 与 inventory
  已复核之后，并必须保留旧候选和差异说明。

#### E. 回归运行预算

- 每次编辑：定向测试。
- 一个纠偏包结束：相关子树、受影响 verifier、类型检查和构建各一次。
- 子阶段 checkpoint：全量单元回归最多一次；只有失败时才做定向诊断和修复后复跑。
- 阶段 closeout：全量 E2E、真实数据和独立审查各一次。
- 资源型 ENOMEM/timeout 必须与产品失败分开记录；允许降低并发后复跑，不得把同一成功结果
  反复包装成新的审计证据。

任何人要求新增审查轮次时，必须先写明：新审查解决哪个尚未覆盖的风险、为何已有证据不能
回答、通过后将解锁哪个门禁。无法回答这三项时，不新增审查，继续当前开发或纠偏主线。

## 6. 阶段收口、展示与交接

1. **阶段性验收**：重新从原始 PRD 核对代码、文档、功能、测试覆盖和术语一致性；把阶段 Draw.io 的当前实体/状态同步到实际代码，逐项判定目标架构和出门条件。不能通过时回开发阶段，不能把图纸涂成全绿。
2. **中文 HTML 可视化报告**：以尽量隔离的 Headless 真实流程测试和新鲜截图展示目标/当前架构、用户路径、通过/失败/未测项、证据与限制。若必须弹窗、抢焦点或影响用户浏览器，先告知用户；仅清理本轮自己创建的浏览器实例和临时件。完成后打开报告和 Draw.io 供人类核查。
3. **独立报告复核**：检查报告是否足以让人类逐项复核本阶段目标；缺少截图、步骤、原始证据或失败解释时补证据，不虚构。若架构与图纸不一致、承诺未实现、测试受阻、计划未完成或偏离 PRD，拒绝声明阶段完成。
4. **Git 同步**：仅在范围内差异、测试和审计核对后提交；保留既有用户改动和历史证据，不以“清理工作树”为由重置、删除或混入无关变更。若无法得到范围清晰的提交，说明原因并停止，不伪称工作树干净。
5. **进展同步**：在阶段结论形成后按 `sync-project-progress` skill 的要求，把已验收/受限/未实现状态、下一计划和证据路径同步到私人助手；不得同步秘密或把本地审计候选写成最终通过。
